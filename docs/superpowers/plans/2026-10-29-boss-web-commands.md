# Boss Web Commands Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Owner web instructions, status questions and follow-up answers reach the same registered Codex Boss and drive genuine GPT/Claude work with durable receipt/reply evidence.

**Architecture:** Vercel authenticates owner/Origin/CSRF and submits bounded typed commands to a distinct-token POST view on the existing PGX status URL. A private SQLite inbox, hidden Windows pull bridge and Boss redeem/resume controller separate accepted/queued/received/dispatched states and deduplicate execution. Existing core ledger/progress/report channels remain authoritative; web sees bounded receipts/replies and cannot select a Boss or forge execution state.

**Tech Stack:** Existing Next.js/TypeScript, PGX Python sqlite3, existing SSH/Windows hidden loop/local Codex queue, tsx/unittest/Playwright. Node >=22.13, no new OAuth scopes/provider keys/Funnel service.

**Spec:** `docs/superpowers/specs/2026-10-29-boss-web-command-design.md`, with approved core and lounge specs in the same directory.

## Global Constraints

- Human approved implementation, end-to-end checks, exact existing-path activation and Vercel deployment. Do not add a second plan/activation approval gate; honor actual tool-policy rejection if one occurs.
- Actual Claude Forge implements W1–W3 after reserved resume/core Tasks1→3→4→5; actual Frame Terra implements W4 UI. One code implementer at a time. Implementer commits exact task files, reports BASE/HEAD/tests, then root dispatches fresh BASE..HEAD gate review before integration/push or next task. Worker never spawns its own reviewer. Never substitute GPT for quota-blocked Claude.
- Existing core Task2/catalog/role labels remain done; core Task6 and lounge L1–L3 integrate rather than duplicate UI/state.
- Same runtime-bound Boss only. No browser UUID/URL/executable/shell/model/actor authority, no newest-session selection, no read-bearer write expansion.
- Body≤16KiB, trimmed text1–4000 Unicode code points, CSRF15min, rate5/min+30/hour, unreceived active≤20, TTL24h, pull15s.
- Send attempts: initial+5s+30s, max3 TOTAL. 120s terminal-notice cooldown, never a fourth send. Queue success≠Boss receipt≠run start≠result approval.
- Terminal raw/reply purge7d, receipt summaries30d; compact private tombstones persist. Unanswered clarification closes30d; already received/started core work never expires via transmission TTL.
- Private runtime0700/files0600; no actual engine names, Boss UUID, keys or runtime paths in public docs/tests/source. No transcript or command text in ProgressV1/metadata/logs.

## Review Focus

1. Two different client IDs submit the same still-pending intent: database equivalent_pending409 prevents duplicate commands/runs (W1).
2. Boss dies after receipt or spawn intent: resumable stage and uncertain child reconcile before any re-dispatch (W3).
3. Web-only user must see clarification/query reply and answer safely without full chat streaming (W1/W4).
4. Multi-instance Vercel, browser timeout, logout or garbage collection cannot weaken idempotency/authentication (W1/W2/W4).
5. Existing HTTPS mapping might reject POST: validate exact view with real distinct-token acceptance before activation; no improvised new public listener (W2/W4).
